팀 지식 공유 검증 개요

설정 오류 사례를 통해 지식의 제안·검토·게시·활용·갱신을 검증했습니다.

해결하려는 문제

개인의 Agent가 알아낸 해결책은 대화가 끝나면 다른 구성원이 찾기 어렵습니다. 반대로 확인되지 않은 내용을 무작정 공유하면 오래된 정보나 잘못된 조건이 팀에 퍼질 수 있습니다. 이 프로젝트는 어떤 지식을 공유하고, 누가 확인하며, 나중에 어떻게 고칠지에 집중합니다.

가상의 팀과 사례

A는 설정 오류가 발생해도 빠진 항목을 알 수 없는 문제를 개선합니다. B의 Agent는 공유된 지식을 검색하고 원본을 확인한 뒤 자신의 예제에 적용합니다. 이후 다른 필수 항목이 추가되자 팀 지식을 갱신하고 다시 확인합니다.

검증 요약. 지식 ID 1건을 v1→v2로 갱신했고, 실제 지식 PR 2건을 사용자가 병합했습니다. 서로 다른 코드·검증 단위의 테스트 총 36개(21+5+5+5)가 통과했습니다. 전체가 각각 독립적인 종단 간 테스트라는 뜻은 아닙니다. 별도 Agent의 v1 활용과 기록을 전달받은 새 세션의 v2 적용을 확인했습니다.

표기: v1/v2는 첫 버전과 갱신 버전을 뜻합니다. 제출본의 지식 파일과 기록은 버전 이름을 통일한 사본이며, GitHub와 Hindsight의 과거 원본 표기는 다를 수 있습니다. 아래 화면은 원본의 일부를 잘라 표시했습니다.

1. 프로토타입GITHUB REPRODUCTION

GitHub PR과 팀 지식 게시 재현

제출 ZIP은 코드 검증용입니다. GitHub PR과 Hindsight 게시는 자신의 Fork를 clone한 Git 저장소에서 재현합니다.

1. 자신의 Fork 준비

제출용 공개 저장소에서 Fork를 눌러 본인 계정에 복사합니다. 이후 PR의 대상(Base)은 원본 작성자의 저장소가 아니라 본인 Fork의 main으로 설정합니다. 기존 PR #5·#6의 이력은 별도 실제 원본 저장소에 보존돼 있습니다.

2. 변경 Branch → PR → 자동 검사

GITHUB_USER=YOUR_GITHUB_ID
git clone "https://github.com/$GITHUB_USER/team-agent-knowledge-showcase.git"
cd team-agent-knowledge-showcase
git switch -c demo/review-date
# knowledge/COMP-015.yaml의 maintenance.review_after만 수정
python scripts/validate.py knowledge
git add knowledge/COMP-015.yaml && git commit -m "docs: revise knowledge review date"
git push -u origin demo/review-date

GitHub에서 base: 본인 Fork의 main, compare: demo/review-date로 PR을 생성합니다. Actions의 validate-knowledge 상태 검사가 통과하면 diff·근거·적용 범위를 사람이 검토하고 병합합니다. 단순 날짜 변경은 PR/게시 경로 재현용이며 신규 bugfix의 실증은 아닙니다.

3. GitHub 보호 규칙과 실제 승인

Settings → Branches / Rulesets에서 main에 PR 필수, validate-knowledge 필수 검사, 강제 Push 차단을 설정합니다. 독립 리뷰어가 있다면 승인 1건을 요구할 수 있습니다. 본인이 만든 PR을 본인이 병합하는 것은 독립된 리뷰어 승인과 다릅니다. Fork에서 Actions가 꺼져 있으면 활성화해야 합니다.

4. 병합 후 Hindsight 게시 — 현재 구현

git switch main && git pull --ff-only
python scripts/reconcile.py --snapshot-commit "$(git rev-parse HEAD)" \
  --source-repository "$GITHUB_USER/team-agent-knowledge-showcase" \
  --bank-id team-knowledge-repro --dry-run

로컬 Hindsight 1.1.0에서 새 Bank(team-knowledge-repro)를 만든 뒤 --dry-run을 제거해 동일 명령을 실행합니다. 실제 동기화와 검색 확인이 필요하며, PR 병합만으로 Hindsight가 갱신되지는 않습니다.

구현 범위. 현재 Actions는 PR 검증만 수행하며 Merge 후 게시 API는 수동입니다. ZIP은 Git 이력이 없어 게시에 사용할 수 없습니다. 상세 재현 절차: docs/GITHUB_SETUP.md. 머지 후 자동화·인증·실행기 설계: docs/AUTOMATION_DESIGN.md.

1. 프로토타입SAME-INPUT COMPARISON

동일 입력의 v1·v2 비교

원본 Git의 실제 두 버전을 같은 입력으로 실행했습니다. v2에서 version이 필수 항목으로 추가된 조건을 보여줍니다.

같은 입력v1 당시 결과v2 결과
{}model 누락 안내model, version 누락 안내
{"model":"demo"}설정 정상version 누락 안내
{"model":"demo","version":"1"}설정 정상설정 정상

왜 갱신해야 했나

두 번째 입력에서 v1은 설정 정상을 반환하지만, 새 요구사항인 v2는 version 누락을 안내합니다. B가 이전 팀 지식만 계속 사용한다면 바뀐 요구사항을 놓칠 수 있습니다.

이는 v1이 당시부터 틀렸다는 뜻이 아닙니다. v1은 model만 검사했고, version 필수 조건은 v2에서 추가됐습니다.

재현 근거

원본 저장소의 v1 커밋 a54e8d6…, v2 커밋 f15b484…에서 같은 함수의 실제 코드를 읽어 실행했습니다. 저장소 README의 명령과 아래 스크립트로 비교할 수 있습니다.

experiments/revision-comparison/compare.py
예제 코드를 실제로 실행하는 스크립트이므로 신뢰한 원본 checkout만 대상으로 사용합니다. 이 결과는 가상 설정 예제에 한정됩니다.

2. 설계 문서WHY THESE FEATURES

요구사항에서 기능을 도출한 이유

Hindsight는 기억의 저장·검색·갱신을 이미 제공한다. 이번 과제에서는 기억 엔진을 다시 만드는 대신, 어떤 지식을 팀에 공개할지 검증하고 승인·갱신하는 과정을 추가했다.

설계의 핵심 결정. Git main의 승인된 YAML을 유일한 지식 원본으로 두고, Hindsight는 Agent가 자연어로 검색하는 파생 저장소로 사용한다. Agent는 제안하고 사람은 근거를 검토한다.
과제에서 필요한 것기존에 제공되는 기능추가한 정책·구현과 선택 이유
개인 경험과 팀 지식 구분Hindsight의 Bank 저장·검색미검증 메모는 개인 기록으로 두고, 증거를 갖춘 내용만 share-knowledge Skill로 후보화. 분류 정책·Skill 구현; 사용자별 ACL은 미구현.
재사용 가능한 지식의 품질Git의 변경 이력 및 Hindsight의 기억 저장적용 범위·제외 조건·테스트 근거·재검토 시점을 YAML로 구조화. validate.py와 CI로 형식을 검사하고 의미·근거는 사람이 검토.
팀에 공유하기 전 승인GitHub Branch·PR·ActionsAgent의 제안은 Draft PR로 제한하고, 병합된 main만 게시. PR/CI 흐름 구현; 독립 리뷰어 강제는 미구현.
다른 Agent가 찾아서 활용Hindsight Recall·MCP 검색검색 결과를 그대로 정답으로 취급하지 않고 Git 원본의 ID·상태·적용 범위를 다시 확인하도록 지침 작성. Agent B 사례 검증; 서버 강제 통제 아님.
새 근거에 따른 갱신·폐기Hindsight의 동일 문서 교체·삭제 API같은 COMP-015 ID를 유지한 v1→v2 변경 PR과 reconcile.py로 반영. 수동 게시 구현; 이전 세션 기억 자동 수정은 미검증.
지속 가능한 관리·추적Git 이력과 Hindsight 문서 메타데이터지식마다 담당자·검토일·갱신 조건·출처 커밋을 기록. 스키마와 운영 절차 구현; 자동 재검증 알림은 후속 과제.
팀 운영 자동화·접근 제어GitHub의 이벤트 실행과 Hindsight REST APIPR 자동 검사까지만 구현. Merge→게시 자동화, 인증된 쓰기 권한·Bank별 ACL·실패 알림은 확장 설계만 작성.

따라서 무엇을 직접 만들었나

구현: 지식 YAML/Schema · 검증기와 GitHub CI · Codex 공유 제안 Skill · Git 승인 원본을 Hindsight에 반영하는 수동 Publisher · 실제 v1/v2 적용 실험.

재사용: Hindsight의 Bank/Recall/문서 API와 GitHub의 PR/Commit/Actions. 후속 설계: 자동 게시, 서버 ACL, 독립 승인 강제, 주기적 재검증.

검증 범위: 본 프로토타입은 가상의 설정 검사 사례 1건이다. 개인 기억만 사용하거나 Git 문서만 사용하는 방식에 대한 반복적 성능 우위 실험은 수행하지 않았다. 구현 상태와 실제 근거는 이어지는 설계·검증 페이지에 구분해 명시한다.

개인 기록과 팀 지식의 기준

검증되지 않은 개인 메모를 바로 팀의 규칙으로 취급하지 않습니다.

무엇을 어디에 두나

구분내용과 사용 기준
개인 Bank작업 중 관찰, 미검증 가설, 개인 메모. 팀의 승인된 규칙이 아닌 탐색 단서입니다.
공유 후보다른 작업에도 쓸모가 있고, 재현 방법·근거·적용 조건을 설명할 수 있는 내용. PR에서는 아직 제안입니다.
팀 지식사람이 검토해 Git main에 병합한 YAML. 검색을 위해 Hindsight 팀 Bank에 별도 게시합니다.

지식 파일의 구성

knowledge/COMP-015.yaml은 ID·revision·상태, 문제와 해결, 적용 조건과 예외, 실행 명령·결과·근거 커밋, 담당자와 재검토 계기를 포함합니다. templates/bugfix.yaml은 작성 예시, schemas/knowledge.schema.yaml은 필수 형식의 기준입니다.

스키마에 제안 전용 상태가 없어 PR 후보에도 active가 들어갈 수 있습니다. 공식 지식인지 여부는 상태 값 하나가 아니라 사람이 main에 병합한 원본인지로 판단합니다.

어떻게 함께 쓰나

B의 Agent는 관련 기억을 검색한 뒤 Git 원본의 ID·상태·버전·범위·근거를 확인합니다. 원본이 없거나 자신의 업무 조건과 맞는지 확인할 수 없다면 적용을 보류하도록 지시합니다. 이는 Agent의 작업 지침이며 서버가 모든 Agent에게 강제하는 통제는 아닙니다.

Bank 이름 구분은 논리적 분리입니다. 현재 서버 측 사용자별 접근 권한과 Publisher 전용 쓰기 권한은 구현·검증하지 않았습니다. 별도 사후 실험에서 개인 Bank에만 저장한 가상 메모가 개인 문서 목록과 검색에는 있었고 팀 문서 목록·동일 질의에는 없었습니다. 이는 라우팅 확인이지 접근 차단이나 과거 PR의 개인 Bank 기원을 입증하지 않습니다.

Skill, PR, 검토자의 역할

Agent는 근거 있는 제안을 준비하고, 반영 여부는 사람이 결정합니다.

Skill이 수행하는 일

Skill 단독으로 처음부터 PR까지 완료된 실행은 이 사례에서 확인하지 못했습니다.

근거실행 가능한 예제, 테스트 명령과 결과, 코드 커밋.

후속 단계사람의 병합 후 Publisher가 게시. PR 작성만으로 팀 Bank는 바뀌지 않음.

무엇을 누가 확인하나

검증기는 필수 필드, 형식, ID와 일부 비밀 패턴을 검사합니다. GitHub Actions는 Python 3.12에서 검사와 테스트를 실행합니다. 사람은 테스트가 주장과 맞는지, 적용 범위와 민감정보 처리에 문제가 없는지 확인하고 병합합니다.

원격 근거 커밋 확인은 --verify-remote를 별도로 실행합니다. 자동 검사 성공은 사실의 의미적 정확성이나 독립 리뷰를 증명하지 않습니다. 이 데모의 PR은 제출자가 직접 병합했습니다.

지식 게시와 갱신 방식

현재는 머지 후 Publisher를 수동 실행합니다.

현재 구현

운영자가 최신 Git main을 받은 뒤 scripts/reconcile.py를 실행합니다. Publisher는 로컬·원격 main과 저장소가 일치하는지, 추적 파일이 깨끗한지, 해당 커밋의 YAML이 스키마에 맞는지 확인합니다.

기존 Bank 문서와 비교해 추가·갱신·삭제 대상을 정합니다. Hindsight에는 POST /v1/default/banks/{bank_id}/memories로 지식 본문, 문서 ID, Git 원본 경로와 커밋을 보냅니다. 같은 ID의 변경은 교체하고, 다른 저장소가 관리하는 문서는 덮어쓰지 않습니다.

실패와 오래된 기억

모든 요청과 마지막 main 재확인이 성공한 뒤 완료 기록을 남깁니다. 도중에 실패하면 일부 문서는 이미 바뀌었을 수 있어 운영자가 최신 상태를 확인하고 다시 실행해야 합니다. 게시나 삭제가 열린 대화·개인 기억·별도 캐시까지 자동으로 바꾸는 것은 아닙니다.

자동 게시로 확장하려면

목표는 검토된 PR이 main에 병합 → 게시 작업 실행 → 결과 확인·실패 알림입니다. 현재 GitHub Actions에는 이 작업이 없습니다. 자동화하려면 로컬 Hindsight에 접근할 수 있는 실행 환경, 서버 인증·게시 전용 권한, 중복 실행과 순서 제어, 재시도와 감사가 필요합니다.

승인과 병합은 다릅니다. 승인만으로는 main이 바뀌지 않습니다. 또한 main 직접 push도 별도로 통제해야 ‘검토된 PR만 게시’하는 정책을 보장할 수 있습니다.

단계구현 시 동작과 검증 기준
① 제안·검사pull_request의 validate.yml에서 Schema·테스트 실행. 쓰기 Secret 없이 검증하고, 통과·사람 검토 전에는 Team Bank를 변경하지 않음.
② 승인된 이벤트PR 병합으로 main이 변경되면 push: branches: [main]이 게시 트리거. 직접 Push를 막는 보호 규칙과 필수 검사·리뷰를 별도 설정해야 '승인된 변경만' 보장됨.
③ 동일 원본 검증게시 실행은 승인된 main Commit SHA 하나를 고정. 최신 원격 HEAD·깨끗한 Checkout·전체 YAML 검증 및 source_repository 소유권 확인.
④ 변경 계산reconcile.py가 전체 Snapshot과 Bank 관리 문서를 비교. dry-run으로 추가·교체·폐기 목록 확인. 다른 저장소가 소유한 문서는 변경하지 않음.
⑤ API 게시Active는 POST /v1/default/banks/{id}/memories, 동일 document_id에 update_mode=replace. Retired는 DELETE /v1/default/banks/{id}/documents/{doc_id}.
⑥ 확인·복구성공 응답, 문서 ID·Commit·검색 결과 확인 후 완료 기록. 오류 시 실패를 남기고 최신 Snapshot으로 재실행; 부분 성공을 전체 완료로 기록하지 않음.
중요한 구분. GitHub PR의 Approve만으로는 게시하지 않습니다. Merge 후 main 변경이 게시 이벤트입니다. Hindsight 문서 교체가 이미 열린 Agent 세션이나 개인 Bank의 오래된 기억까지 갱신하는 것은 아닙니다.

자동 게시를 실제 구축하기 위한 조건

개인 노트북의 로컬 실험과 팀 운영 환경을 분리하고, 인증·실행기·장애 대응을 순서대로 구현합니다.

운영 방식설정과 현실적인 제약
단계 A · 현재사람이 PR을 병합하고 로컬에서 reconcile.py --snapshot-commit을 실행. Hindsight는 127.0.0.1:8888. GitHub에는 게시용 인증정보를 보관하지 않음.
단계 B · 단기 자동화같은 신뢰된 Mac에서 launchd 등의 주기 실행으로 git fetch→최신 main 확인→전체 Snapshot Publisher를 자동 호출. 네트워크 노출 없이 로컬 API 사용 가능하나 Mac이 꺼져 있으면 지연됨. 미구현.
단계 C · 운영 자동화GitHub Actions가 보호된 main 변경을 감지해 인증 가능한 Hindsight HTTPS 엔드포인트에 게시. 현재 Client에는 인증 헤더가 없어 먼저 추가·테스트해야 함. Runner의 네트워크 접근과 권한 분리가 전제. 미구현.

운영 자동화 구현 체크리스트

1. GitHub. .github/workflows/publish.yml 추가: push(main) + 필요시 workflow_dispatch, contents:read, concurrency 직렬화. main PR·검사·리뷰 보호를 설정하고 워크플로 파일도 검토 대상에 포함.

2. 네트워크·인증. GitHub-hosted Runner는 Mac의 localhost에 연결할 수 없음. 인증된 HTTPS API 또는 격리된 신뢰 실행기 확보 후, Publisher HTTP Client에 인증 헤더·타임아웃·Secret 마스킹 구현. 공개 저장소의 Self-hosted Runner에 외부 PR 코드를 실행시키지 않음.

3. 게시 안정성. 구버전 작업이 최신 Snapshot을 덮어쓰지 않게 실행 순서 제어·HEAD 재확인, 동일 ID 재시도, 429/5xx 재시도, 문서 폐기 범위 제한. 401/403은 즉시 실패하고 경고.

완료로 인정할 자동화 테스트

(a) 미병합 PR은 Team Bank 무변경 → (b) 병합 후 동일 지식 ID 1건 게시 → (c) 다음 Merge에서 같은 ID 교체 → (d) retired 병합 시 소유 문서만 삭제 → (e) 서버 장애·중복 Merge에서 최신 Snapshot으로 복구. 결과에 PR·Commit·Actions Run·API 응답을 함께 기록.

자세한 구성 예시와 보안 가정은 docs/AUTOMATION_DESIGN.md, 평가자용 Fork·PR·수동 게시 실습은 docs/GITHUB_SETUP.md에 정리했습니다.
