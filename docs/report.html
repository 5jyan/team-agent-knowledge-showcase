1. 프로토타입 01 / EXAMPLE

설정 오류를 이해할 수 있게 바꾸기

프로그램을 실행하는 데 필요한 설정이 빠졌을 때, 무엇을 고쳐야 하는지 알려주는 예제입니다.

어떤 문제가 있나

가상의 팀에서 설정 파일에 model이라는 필수 항목을 넣어야 하는 프로그램을 사용합니다. 이 항목이 빠진 채 실행하면 기존 프로그램은 “설정 오류”라고만 표시합니다. 사용자는 어떤 값이 빠졌는지 알 수 없어 설정을 하나씩 살펴봐야 합니다.

무엇을 개선했나

상황프로그램의 결과
기존설정 오류
개선설정 오류: model 항목이 없습니다
정상 설정model과 version 항목이 모두 있으면 설정 검사를 통과합니다.

왜 팀 지식으로 남기나

A와 Agent가 이런 개선을 확인해 근거와 함께 공유하면 B의 Agent도 자신의 설정 검사에서 무엇이 빠졌는지 알려주는 방식을 고려할 수 있습니다. 적용 전에는 자신의 프로그램에도 같은 조건이 맞는지 확인해야 합니다.

이후 model과 version이 둘 다 없을 때 하나만 표시되는 한계를 확인해 빠진 항목을 모두 알려주도록 지식을 갱신했습니다. 아래 3번에서 갱신 전후 결과를 구분합니다.

현재 상태. 새 예제의 코드와 첫 지식은 PR #5를 통해 병합했고 Hindsight에 수동 게시했습니다. 별도 B Agent의 활용을 확인했고, 후속 갱신도 PR 병합과 수동 게시 후 확인했습니다.

1. 프로토타입 02 / REPRODUCTION

실행과 결과 확인

같은 입력에 대해 기존 메시지와 개선 메시지를 비교하고 정상 설정도 함께 확인합니다.

확인할 입력과 예상 결과

입력확인할 결과
model 항목 없음기존 방식은 설정 오류, 개선 방식은 설정 오류: model 항목이 없습니다를 표시합니다.
model 항목 있음설정 검사를 정상 통과합니다.

저장소 루트에서 다음 명령을 실행합니다. 

python3 examples/config-validation/run_demo.py
python3 -m unittest discover -s examples/config-validation -p 'test_*.py' -v
실제 데모는 입력에 model이 없을 때 기존 설정 오류와 개선된 설정 오류: model 항목이 없습니다를 출력했습니다. model과 version이 둘 다 있을 때는 두 방식 모두 설정 정상을 출력했습니다. 현재 r2의 누락·정상·설정값 미노출 테스트는 5개가 통과합니다.

위 결과는 새 예제 코드를 로컬에서 실행한 것입니다. 사용자가 첫 지식을 병합한 뒤 팀 Bank에 수동 게시하고 검색했습니다. 별도 B Agent가 지식을 검색하고 자신의 예제에 적용했습니다.

2. 설계 문서 01 / PROBLEM

무엇을 해결하려는가

한 사람이 확인한 개선 사항을 다른 구성원의 Agent가 근거와 함께 활용하고, 새 정보가 생기면 갱신합니다.

가상의 팀과 업무

A와 B가 설정 파일을 사용하는 개발팀에서 일합니다. 기존 프로그램은 필수 model 설정이 없어도 단순히 “설정 오류”라고만 표시합니다. A와 Agent는 오류에 누락된 항목을 표시하도록 개선하고 테스트합니다. B의 Agent는 팀 지식을 검색해 비슷한 설정 검사 작업에 참고할 수 있습니다.

공유할 정보는 개선 결과뿐 아니라 어떤 상황에서 확인했고, 어떤 테스트를 실행했으며, 어디까지 적용되는지입니다. 설정값이 민감할 수 있으므로 오류에는 값 자체를 넣지 않습니다.

개인 기록과 팀의 공식 지식

작업 중 추측과 개인 메모는 개인 Bank에 둡니다. 근거가 생기고 다른 사람에게 쓸모가 있는 내용은 공유 후보가 됩니다. 사람이 검토해 Git의 main에 반영한 지식만 팀의 공식 원본으로 취급합니다. Hindsight의 팀 Bank는 그 내용을 찾기 위한 검색 공간입니다.

검색 결과가 보여도 B의 Agent는 원본의 ID·상태·버전·적용 조건·근거를 다시 확인하도록 지시받습니다. 원본을 확인할 수 없거나 자기 작업에 적용할 근거가 부족하면 사용을 보류합니다. 이 지시는 모든 Agent에게 강제되는 보안 장치가 아닙니다.

현재 상태. 새 사례의 첫 지식 COMP-015 r1은 PR #5 병합 후 팀 Bank에 수동 게시하고 검색 결과를 확인했습니다. 별도 B Agent가 지식을 검색하고 자신의 예제에 적용했습니다.

2. 설계 문서 02 / FLOW

전체 흐름과 역할

제안, 검증, 병합, 게시, 활용을 분리해 각 단계의 책임을 명확히 합니다.

순서실제 수행 주체와 결과
1. 발견A와 Agent가 기존·개선된 메시지를 같은 입력에서 실행하고 테스트 결과를 확보합니다.
2. Skill 실행Codex에서 $share-knowledge를 호출하면 Agent가 기존 지식을 확인하고 후보 파일과 draft PR을 작성합니다.
3. 자동 검사GitHub Actions가 지식 형식 검사와 테스트를 실행합니다. 실패하면 원인을 수정하고 다시 검사합니다.
4. 사람의 검토사용자가 변경 내용, 근거, 검사 결과와 적용 범위를 살펴보고 GitHub에서 PR을 병합합니다.
5. 수동 게시운영자가 최신 main에서 Publisher를 직접 실행해 Hindsight 팀 Bank에 반영합니다.
6. 사용과 갱신B의 Agent가 검색·원본 확인 후 활용합니다. 새 조건이 발견되면 같은 ID의 새 버전을 PR로 제안합니다.
책임 분리. Skill은 제안자, 자동 검사는 형식과 테스트 확인자, 사람은 내용 검토·병합 결정자, Publisher는 병합 후 게시 담당입니다. 이 데모에서는 한 사용자가 검토자와 운영자 역할을 함께 합니다.

GitHub의 승인(review approval)과 병합(merge)은 다릅니다. 승인은 의견 표시이고, 병합돼야 변경된 파일이 공식 원본인 main에 들어갑니다. 현재 구현은 승인 여부를 API로 강제 검증하지 않습니다.

2. 설계 문서 03 / SKILL

Codex Skill은 무엇을 하는가

Skill은 Agent가 지식을 일관된 절차로 제안하도록 만든 지침 파일입니다.

구성과 호출

실제 실험에서는 별도 스킬 저장소의 skills/share-knowledge/SKILL.md를 사용했습니다. 이 제출용 저장소에는 경로를 수정한 사본 .agents/skills/share-knowledge/SKILL.md이 있습니다. Codex에서 $share-knowledge를 호출하며, 현재 저장소 루트 또는 TEAM_KNOWLEDGE_REPO로 지정한 경로에서 지식 원본을 찾도록 사본을 수정했습니다. 실제 저장소의 스키마와 기존 문서가 스킬 속 예시보다 우선합니다.

순서Skill 지침에 따른 Agent 행동
기존 지식 확인README·스키마·기존 YAML을 읽고 같은 내용이 있는지, 기존 ID를 수정해야 하는지 비교합니다.
근거 수집문제·개선·적용 조건·제외 조건과 실행 명령, 테스트 결과, 근거 커밋을 정리합니다.
후보 작성새 브랜치에 knowledge/COMP-015.yaml 같은 후보를 작성합니다. 비밀정보는 제외합니다.
검사와 제안검증기·테스트·diff를 확인하고 GitHub에 draft PR을 만듭니다.
스킬의 금지 사항. 스킬은 스스로 PR을 승인·병합하거나 Hindsight 팀 Bank에 직접 쓰지 않습니다. Skill은 Agent에게 주는 작업 지침이지 서버 권한을 막는 기술적 통제는 아닙니다.

새 사례에서는 별도 Codex 실행이 사용량 한도로 중단된 뒤, 현재 세션에서 동일 스킬 절차를 이어 PR을 완성했습니다.

2. 설계 문서 04 / KNOWLEDGE TEMPLATE

지식 템플릿은 어떻게 구성되는가

지식을 한 문장의 조언으로만 저장하지 않고 다른 사람이 확인할 수 있는 근거와 한계를 함께 둡니다.

templates/bugfix.yaml을 참고하고 schemas/knowledge.schema.yaml에 맞춰 knowledge/COMP-015.yaml을 작성합니다. 현재 스키마는 버그 수정 유형을 대상으로 합니다.

필드역할과 예시
id / revision / statusCOMP-015, r1, active. 지식의 번호와 버전, 상태를 구분합니다.
problem / cause“무엇이 문제였는지”, “왜 발생했는지”를 적습니다. 예: 누락 항목 이름이 오류 메시지에 없음.
solution / summary개선 내용을 기술합니다. 예: model 누락 시 해당 항목명을 안내.

상태 해석. 스키마에 proposed 상태가 없어 PR 안 후보에도 active가 들어갑니다. PR이 병합되기 전에는 제안일 뿐이며 공식 지식이 아닙니다.

템플릿의 예시 값은 구조를 보여주기 위한 자리표시자입니다. 실제 후보에는 수행한 테스트와 실제 커밋을 넣습니다.

2. 설계 문서 05 / VALIDATION

무엇을 누가 검증하는가

기계가 확인할 수 있는 조건과 사람이 판단해야 하는 내용을 나눕니다.

검증 주체확인하는 내용과 한계
Agent / 제안자같은 입력에서 변경 전후 메시지와 정상 입력을 실행하고 테스트를 작성합니다. 후보가 실제 실행 결과와 일치하는지도 살펴봅니다.
지식 검증기scripts/validate.py knowledge가 필수 필드, 스키마, ID와 파일명, 중복, 일부 비밀 패턴 등을 검사합니다. 패턴 검사는 모든 비밀정보를 찾아내지 못합니다.
GitHub ActionsPR과 main push에서 Python 3.12를 설치하고 지식 검증과 저장소·예제 테스트를 실행합니다. PR #5에는 설정 예제 테스트가 추가됐습니다.
원격 근거 검사--verify-remote를 별도 실행하면 지정한 GitHub 커밋에 접근 가능한지 확인합니다. 현재 기본 CI에는 포함되지 않습니다.
사람테스트가 주장과 실제로 맞는지, 적용 범위와 민감정보 처리에 문제가 없는지 검토한 뒤 병합을 결정합니다.
검증의 한계. 스키마 통과, 커밋 존재, CI 성공은 내용 자체가 옳다거나 독립된 사람이 승인했다는 증거가 아닙니다. 이번 PR의 검토·병합은 제출자가 직접 수행했습니다.

r1에서 model 누락 전후 메시지, 정상 입력, 설정값 미노출 테스트 3개를 실행했고, r2에서는 필수 항목 누락에 대한 테스트가 5개로 늘었습니다.

PR은 어떤 내용을 담는가

PR 파일 구성

이번 PR #5에는 가상의 설정 검사 예제·테스트, CI에서 예제 테스트를 실행하는 변경, 지식 후보 knowledge/COMP-015.yaml이 포함됩니다. 코드와 테스트를 담은 커밋을 먼저 만들고, 지식 파일은 그 커밋을 근거로 참조합니다.

PR 본문의 구성

항목이번 후보에 담은 내용

2. 설계 문서 07 / CURRENT PUBLISHING

병합 후 Hindsight에 반영하는 방법

목표는 PR 머지 후 자동 게시입니다. 이번 프로토타입에서는 로컬 Hindsight를 사용해 게시 프로그램을 수동으로 실행했습니다.

현재 실제 실행 순서

사용자가 PR을 병합한 뒤 운영자가 지식 저장소에서 최신 main을 받고 검증합니다. Python 가상환경과 로컬 Hindsight API가 준비됐다고 가정한 명령입니다.

git switch main
git pull --ff-only origin main
python scripts/validate.py knowledge --verify-remote
python scripts/reconcile.py --snapshot-commit "$(git rev-parse main)" \
  --bank-id team-compiler --dry-run
python scripts/reconcile.py --snapshot-commit "$(git rev-parse main)" \

--dry-run은 계획을 확인할 뿐 Bank에 쓰지 않습니다. 마지막 명령을 실행해야 실제 게시를 시도합니다.

Publisher가 하는 일

지정한 커밋이 로컬 및 원격의 현재 main인지, 저장소가 맞는지, 작업 파일에 추적된 변경이 없는지 확인합니다. 해당 커밋에 저장된 스키마로 YAML을 검사하고 팀 Bank의 기존 문서와 비교해 새 문서·변경된 문서·삭제 대상·건너뛸 문서를 결정합니다.

게시 요청은 POST /v1/default/banks/team-compiler/memories로 전송하며, 지식 본문과 document_id, 원본 커밋 등의 메타데이터를 담습니다. 현재 클라이언트는 async: false로 요청합니다. 실행 후 문서 조회와 recall로 확인해야 검색 결과까지 검증할 수 있습니다.

프로토타입 검증 범위. 목표는 병합 후 게시 프로그램을 자동 실행하는 것이지만, 현재 GitHub Actions에는 게시 작업이 없습니다. 로컬 환경에서는 같은 Publisher를 직접 실행해 Git 원본 검증과 Hindsight API 반영을 확인했습니다. 자동 실행 경로는 아직 구현·검증하지 않았습니다.

2. 설계 문서 09 / AUTOMATION PROPOSAL

목표 운영 방식: 머지 후 자동 게시

팀 서비스에서는 PR이 병합되면 게시 프로그램이 자동 실행되도록 설계합니다. 이 경로는 아직 구현·검증하지 않았습니다.

제안하는 흐름

사람이 검토한 PR을 main에 병합 → main 변경 이벤트가 게시 작업 시작 → 최신 main과 게시 정책 확인 → Publisher 실행 → Hindsight 문서 조회 및 검색 확인 → 성공·실패 결과를 운영자가 확인.

승인만으로 게시하지 않습니다. 승인 후에도 PR이 병합되지 않거나 내용이 달라질 수 있기 때문입니다. main에 직접 push하는 경우도 이벤트가 발생할 수 있으므로, “PR 승인 후 병합만 허용” 정책을 GitHub에서 별도로 강제하고 게시 작업에서도 해당 조건을 확인해야 합니다.

운영 환경에 필요한 조건

항목추가로 필요한 조치
실행 위치현재 Hindsight는 개인 Mac의 127.0.0.1:8888에 있습니다. GitHub가 제공하는 원격 실행기에서 이 주소는 그 실행기 자신을 뜻하므로 접근할 수 없습니다. 서버가 닿는 실행 환경이나 연결 가능한 서비스가 필요합니다.
인증과 권한현재 Publisher는 API 인증 헤더가 없습니다. 인증을 지원하는 게이트웨이 또는 클라이언트 변경과 게시 전용 자격증명 관리가 필요합니다.
중복과 순서여러 실행기·컴퓨터 사이의 분산 잠금과 순서 제어가 필요합니다. 현재 잠금은 같은 checkout 안에서만 동작합니다.
장애 대응실패 알림, 재시도, 게시된 버전 추적, 운영자 점검과 롤백 절차가 필요합니다.
현재 프로토타입에서는 GitHub의 자동 실행 대신 운영자가 동일한 게시 프로그램을 수동 실행해 로컬 Hindsight 반영을 검증했습니다. 자동 실행 경로 자체는 구현·검증되지 않았습니다.

2. 설계 문서 10 / OPERATIONS

안전하게 운영하려면

팀 지식을 오래 유지하려면 게시뿐 아니라 검토 주기, 불일치와 권한을 관리해야 합니다.

실패와 재실행

게시 도중 API가 실패하면 이전에 처리된 문서는 이미 바뀌었을 수 있습니다. Publisher는 모든 요청과 마지막 main 재확인이 성공한 뒤에만 완료 상태를 기록합니다. 운영자는 최신 main과 Bank 상태를 확인한 뒤 재실행합니다. Git과 Bank 사이의 순간적인 불일치나 부분 반영이 불가능하다고 주장하지 않습니다.

재검토와 폐기

지식마다 담당자, 재검토 날짜, 코드나 테스트 변경 같은 수정 계기를 기록합니다. 내용이 더 이상 유효하지 않으면 변경 PR로 상태와 근거를 남기고 반영합니다. 팀 Bank에서 삭제해도 개인 기억이나 이미 열린 대화에서 이전 내용이 사라지는 것은 아닙니다.

접근 범위와 보안

개인 Bank와 팀 Bank의 이름은 라우팅을 나누기 위한 것입니다. 현재 서버 측 Bank별 ACL과 Publisher 전용 쓰기 권한은 구현·검증하지 않았습니다. 팀 단위 운영에는 인증, 읽기·쓰기 권한, 감사 기록, 비밀정보 처리 정책이 필요합니다.

대안과 평가 범위

개인 기억만 쓰는 방식은 공유 근거가 약하고, Git 문서만 쓰는 방식은 원본 관리가 단순하지만 관련 문서를 찾는 과정이 추가됩니다. Hindsight와 Git을 결합하면 검색과 원본 확인을 함께 사용할 수 있지만 게시와 불일치를 관리해야 합니다. 새 사례에서 세 방식의 비교는 아직 수행하지 않았으므로 정확도·효율성의 우위를 주장하지 않습니다.

실제 관찰 결과와 남은 한계, 후속 우선순위는 3~4번에서 실행 기록과 함께 정리합니다.

초기 요청은 “github hindsight 받아서 로컬에 구축해줘”, “자 우리 이제 개발 해야할 순서명세해”, “내 깃헙에 레포 파서 작업해줘”였습니다. 이후 “우리 스킬도 만들기로 했잖아. 그걸로 preㅗ 날려야지. 그리고 클로드코드 세션이 아니라 코덱스로 하면 되지”라고 요청해 Codex Skill 기반 PR 생성 흐름을 선택했습니다.

첫 Skill 실행 요청

실제 지시의 핵심은 다음과 같습니다.

“기존 구현은 막연한 '설정 오류'만 출력하지만 개선된 구현은 '설정 오류: model 항목이 없습니다'라고 구체적으로 알린다. … 실제 코드를 보여주고, 변경 전과 후의 입력과 출력 및 테스트로 사실을 검증하라.”
